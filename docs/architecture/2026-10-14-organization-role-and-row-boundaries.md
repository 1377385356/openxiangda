# 组织角色与 Native 行边界

状态：实现前架构记录，2026-10-14。范围由既有多组织平台决定与本次验证要求确定；不新增客户业务角色。

## 问题与所有者

V2 role union、唯一 membership 键和 RLS 仍以 environment/user/role 组成授权；相同人和来源班级 ID 跨企业会共用范围。平台已有组织、安装、成员与目录来源事实，应用只声明来源事实到业务角色/维度的映射，不复制目录或推断身份。平台唯一拥有派生角色投影、手工授权、可信组织和数据边界。

## 声明与不变量

应用角色显式选择 organizationReach=self/subtree；未声明保持既有无组织兼容。authz.directoryRoleSources 将中性的 source/roleFactCode 映射到 roleCode，并声明 scopeType→dimensionCode 与 operations。来源值是字符串，不冒充 Native 记录 UUID。目录映射角色必须声明 self，空范围不能变成全校。每次当前用户授权准备从当前租户/组织的活动安装、成员、主体与事实计算有界派生 membership；同一角色在两个组织有不同稳定 binding，scope grants 永不跨校合并。原始目录仍只有平台一份。

手工组织角色授权要求明确目标组织、目标用户活动成员及合法管理员；源映射角色不允许手工覆盖。委托授权缺组织覆盖契约时失败关闭，不能扩大到其他学校。平台组织管理权限不自动成为应用业务管理员，上级普通成员不获得 subtree。

资源组织策略为 none/owned/inherited-down。none 保留既有语义；其他策略使用平台不可由业务字段篡改的 organization_id 归属。创建绑定可信当前组织；更新不得改变归属；未知历史归属不推断、不回填。owned 按该次操作同一 membership 的组织 reach 与行/字段范围共同授权；inherited-down 仅增加获准祖先内容的读取，修改仍按原归属。不能先合并组织范围再用另一个角色的班级范围，否则多角色会串用。

## SQL 与缓存执行

角色与记录增加可空组织维度，不搬迁现有数据。发布只使用新增正式 SQL。当前 Head 的 canonical_json 保存声明；服务端和 PostgreSQL RLS 共同检查活动来源。预备读取上下文在同一 SQL statement 解析一次；每行按自身组织过滤同一批有操作/字段能力的 membership，再执行原行策略。默认无组织声明保持原策略。直接记录 ID、列表、导出、聚合、关联与子表共同经过相同 RLS；不能以 controller 的 WHERE 代替。

目录派生授权仅由平台所有者在当前用户/组织范围内有界准备，保留稳定 ID、来源摘要和组织键，变化推动原授权版本。SQL 再查来源有效性，旧缓存或已退休事实不能继续写。身份、Head、组织、来源摘要均参与缓存/意图绑定。未提供可信组织的组织资源请求失败关闭，服务/后台路径不从请求 body 获取组织，也不自动使用全区身份；需要单独明确的系统操作边界。

## 失败、并发与资源

目录源读取失败、超出事实/维度预算、绑定冲突、成员/安装撤销及无工作组织均有显式拒绝；不保留旧事实作无限期授权。单用户/组织派生使用稳定锁与同一事务快照，不能把不完整同步视为退休。事实最多 512、来源 32、角色 32；维度值沿现有授权容量验证，超限拒绝而非截断。查询/投影无外部消息副作用。

## 安全与回滚

业务表/源码不保存学校 Secret、unionId、raw 或第二套用户库。组织由平台验证；业务输入不能更改保留列。旧应用与租户未声明策略时保持原行为。新增结构可保留；启用组织角色/数据策略后，只能回到仍执行边界的兼容版本或向前修复，不能用旧镜像开放受保护数据。

## 可证伪验证

真实 PostgreSQL 验证：同源用户/班级 ID 跨学校、同人 teacher/guardian/head_teacher 多范围、多角色不能串用；self 拒绝兄弟/后代、subtree 只覆盖获授树；inherited-down 可读祖先且不可改；无组织、未安装、非成员、退休主体/事实及篡改保留列拒绝；NULL 历史归属不放行；任意直接 ID、批量、聚合、导出、子表及关联同边界。源读取、SDK、SQL/RLS、节点运行和真实角色浏览器分别记录，不互相替代。


## 读取事务与缓存补充

目录角色准备由平台自己的有界写事务完成，不在 Native 只读事务中写权限。与当前请求已经持有的角色锁冲突时 NOWAIT 拒绝，不能自锁等待。授权缓存不保存未提交的 snapshot；显式 fresh 和事务内核对均绕过快照缓存。Native 行权限继续重查当前来源，目录准备成功不代替写入/外部业务动作的 fresh 授权。

组织上下文的读取暂不使用两层授权缓存；每次核对并准备当前目录投影。明确 fresh 及任何 transaction manager 不读写内部快照缓存；Redis epoch 不可用时重新解析，不依赖无权威 epoch 的缓存。目录 prepare 只提交自己的事务，源变化之后旧 projection 当次 SQL 即拒绝；Head 在准备期间变化则要求刷新。已启用资源不能通过下一版本移除组织策略，记录组织在数据库触发器中不可改；唯一键按组织分区，子表复合外键绑定同一组织。未启用资源保持原列和索引；无组织服务身份不获组织资源权限。

## 已有业务动作入口的组织边界

现有 Native 业务动作把已经验证的当前用户转换为 application principal，用原 platformAccess 和业务动作 proof 约束副作用。组织资源不能让转换抹掉用户边界。转换时只从可信当前 principal 派生内部 organizationActor（用户、工作组织、授权版本、绑定 ID），不接受 body/header。保留原签名与声明验证，再由 SQL 对同一条仍有效且有该动作能力的 membership 结合组织 reach 和数据行策略；同一绑定同时覆盖变更前后。字段写入继续由原动作声明及服务端实现约束，不创建新的身份或后台全区身份。普通 application/定时/服务令牌没有该证明时，组织资源拒绝。RLS、记录所属组织触发器与 Native 事务预检都执行该边界。Connected Dev 的短期 proof 和 source invocation proof 绑定组织字段；错误、源撤销、组织不匹配、缺少事实和权限版本变化失败关闭。

组织资源的 `organization_id` 是有界查询/聚合可用的只读平台元数据；普通资源不增加不存在的列。应用按该字段做区/校统计，无需创建第二个学校归属字段或读取原始数据库。服务端字段写入检查和数据库触发器都拒绝修改，记录读回仍经过同一 RLS。
