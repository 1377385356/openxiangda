# 增量发布验证

状态：实施。维护者要求控制小改动发布时间，避免把完整浏览器和参考应用矩阵重复作为每次发包前置。

## 问题与归属

发布验证计划已经区分 guidance 与 runtime，但发布入口在读取计划之前强制要求独立参考应用。Skill 和文档检查排在昂贵的浏览器与参考应用之后，文档错误能导致整轮重试。回执以 HEAD 为单位失效，无法表示未变化的浏览器运行内容已经通过。

发布计划是验证范围的唯一所有者；发行器执行计划，不另加隐式全量条件。Changesets 仍决定版本，制品清单仍决定待发布字节，现有回执仍决定发布阶段。

## 决定和不变量

- 先构建必要产物，再检查 Skill、文档，然后运行相关包测试及打包验收。不重复执行候选包仅因依赖版本传播触发的整套依赖测试；依赖 build 仍由 Turbo 图保证。共享 core/runtime 变化扩大到候选消费者验证。
- 只有计划要求 reference 时才核对、准备和绑定参考应用。准备入口仅安装、CLI check 并产生锁文件，正式 check/test/build/浏览器验收在 verify:release 执行一次。历史回执缺失范围字段时仍要求 reference；不能用缺少字段绕过原门禁。发行器根据已验证制品重新计算范围并拒绝不匹配。
- 浏览器测试可复用 24 小时内的成功记录。键包含真实候选运行文件、生成应用内容、规范化后的实际安装依赖锁、维护者 fixture、验证脚本、Node/OS/架构及测试环境。只排除明确的说明资料和发布说明元数据；包语义、外部依赖 integrity、版本与运行代码变化均失效。
- 当前 tarball 的安装、内容、Skill 和防篡改验收仍执行。缓存不替代最终 HEAD/tarball 回执，不代表线上业务通过。live 测试、有外部目标或 full 审计不使用浏览器缓存。失败和超时不记录通过。
- `verify:release:full` 显式执行完整矩阵；普通验证记录阶段耗时，并为子进程设置预算，超时终止进程组而不是降低测试范围。

## 影响、并发与回滚

仅维护者脚本/规则变化，无应用运行时、用户权限、V1 引擎或生产数据变化。现有发布进程锁、主线包含、不可变 npm 版本、渠道恢复和制品校验不变。缓存原子写入，只保存摘要、时长和结果，不保存凭据。不同输入不会覆盖同一成功记录。

回退此提交恢复旧全量流程。已开始 npm 写入的回执继续遵守原有恢复规则，不以优化为由重选版本或制品。

## 验证

使用真实临时目录测试缓存命中、资料变化、运行代码/依赖/执行器变化、过期、强制执行和失败重试；范围测试验证 metadata/guidance 不要求 reference、core/未知变化仍要求；发布阶段测试验证无 reference 的合法路径和旧回执的拒绝边界。运行相关脚本测试、文档构建和已有包/回执防篡改测试，不为修改验证调度器再次发包。
