# Mobile entry completion and draft affordances

2026-09-06. Evidence: acceptance screenshots show create returning to desktop list, page padding overriding mobile entry, unconditional draft prompt during edit, date-wheel truncation, radio alignment and upload/address affordance defects.

Owner: SDK generated entry owns completion/navigation; resource draft client owns persisted drafts; scoped mobile field kit owns touch presentation. No application overrides or second data store.

Invariants: successful create/update navigates to returned record detail when selected, drawer submit transitions to readonly detail in place. Failed writes retain form and do not navigate. No detail permission is added; absent detail selection retains existing fallback. Editing loads the authoritative record and never automatically prompts to restore a saved draft; explicit draft-box/new-page draft requests remain supported. Draft badge reflects scoped server results, is hidden at zero, and is in footer. Server draft CAS and atomic submit remain unchanged.

Contracts: completion callbacks, existing route manifest, scoped CSS and field values. Date intervals preserve exact stored endpoints and validation, while each endpoint renders intact. Address ellipsis changes presentation only and accessible text retains the full address. Upload limits, retry/removal and ownership do not change.

Bounds/concurrency: retain submit busy guard, request cancellation and stale-response handling; no extra broad data reads; no new permissions. CSS scoped to mobile ancestry. Stable 1.x and other deployed package versions unaffected. Rollback: previous immutable SDK package and Demo frontend/config revision.

Falsifiable checks: create submit reaches saved record detail; drawer submit opens readonly returned record; edit with a saved draft has no automatic modal; badge zero/nonzero; 320/390px mobile page/header bounds; equal radio icon centers; full date column text and separate datetime endpoint lines; centered upload icon; ellipsized address with separate clear button. Existing failure/draft/file regression suites remain applicable.

Detail redesign is an independent review artifact in the thread visualization folder; it is not silently substituted for approved runtime design. Workflow entry/edit ownership is investigated separately before implementation.

## Workflow launch drawer

Existing workflow submission remains the sole owner of atomic process commands, requirements and polling. An optional drawer presentation uses the same component with transient local command ID, keeps close disabled during request/processing, and calls the parent with the committed subject ID only after the process starts. The parent opens the selected readonly record detail. Independent workflow launch retains its manifest-based instance navigation. No duplicate form or command implementation.

## Workflow record editing (updated user decision)

The user clarified that editing a completed workflow record must feel exactly like ordinary data editing. The generated CRUD and workflow-owned edit entry therefore share one form and drawer presentation: “编辑数据”, the normal submit button and the existing change history. There is no correction-specific explanation, reason, confirmation or audit step. The Workflow service's internal Surface/command may remain the transport owner, limited to current application administrators; its names do not become business UI. SDK renders server-issued editable fields and preserves expectedRevision, while Native transactions and change history remain authoritative. Saving changes the live business record without starting another approval or changing the existing approval outcome. The unchanged payload retains its idempotency key on retry and never silently reloads a newer revision before saving. Server implementation decision: sy-lowcode-platform-server/docs/architecture/workflow-record-correction-v2.md.

The user's further clarification requires the ordinary complete edit interaction, without an “edit application” popup. Desktop detail and edit use the platform's single drawer transition with shared width/full-screen state, then return to the same readonly record. Direct list editing opens that same ordinary form. The mobile detail stays on its current page and switches between the shared mobile form and readonly content; no extra edit dialog or approval confirmation is introduced.

The shared-subtable browser test exposed a lifecycle defect: setting its loaded marker before a read completes causes React StrictMode cleanup to discard the only response and the next effect to skip loading. SubtableField must mark a parent loaded only after an active read succeeds. Cancelled or failed reads remain retryable, with the existing scope, row limits and Native source unchanged. This is verified through the ordinary workflow record form loading and editing existing child rows.

Subtable controls and transaction encoding use the existing selectedSurfaceFields contract: form selection owns editable fields, while detail selection owns readonly display. Hidden and unselected fields are not sent; the declared parent and order fields remain structural transaction inputs. A child resource's generated flags control standalone pages, not row permissions. Deleting a child row therefore uses the same current-user delete capability as the subtable control, even when the auxiliary resource has no generated pages.

### Entry lifecycle verification

The same unchanged launch payload retains one idempotency key after a transport failure. Drawer completion fires once per command even when its parent renders again. Close handlers consult the synchronous in-flight guard as well as processing state. A failed status read has an explicit in-place refresh action, preserving the committed command. The new-page action uses the verified launch path and carries an already committed command ID; before submission its tooltip explicitly says unsaved input is not transferred. Workflow-owned edits load only for the current administrator and initialize the shared mounted form from a validated, matching server Surface. Changing identity, environment, resource or record discards the old Surface; CAS failures retain the original revision and input. Only server-issued editable, visible, nonsystem fields participate in encoding. Files, images, signatures and rich text use ordinary FieldKit controls and Native upload/validation; prior attachment availability is not an additional guarantee. Subtables reuse the normal initial load and buildSubtableOperations plan. The internal save input carries only the standard DataTransactionOperation array, with the parent update and its expectedRevision first, followed by bounded child create/update/delete operations; Native owns the single transaction and change history. Existing mobile launch uses the same command lifecycle with its mobile controls. Administrators edit from the existing mobile record detail on the current route, and saving restores that record's readonly detail in place.
