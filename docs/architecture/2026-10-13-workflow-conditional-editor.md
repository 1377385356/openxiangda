# 条件人员规则 PC 编辑闭环

## 问题与所有者

已有运行入口与 Source v2 导出支持条件人员，但 PC 只能编辑平铺人员，草稿新绑定仍拒绝条件。平台拥有当前 AppVersion、发布定义、办理覆盖、权限和 CAS；SDK 只编辑完整 assignment 并提前校验。沿用已确认的条件人员设计，不另建解析器或状态存储。

## 不变量与边界

- 工作流级 `conditionalAssignment` 只读上下文包含发布定义、精确来源和节点范围维度，不含共享草稿、完整业务步骤目录或服务凭据；缺失上下文时不开放编辑。
- catalog 的 `conditionalAssignments: true` 是新增草稿节点的能力提示。服务端必须自行重新读取上下文并校验，不信任浏览器声明。
- 条件值是一个整体。表单、冲突刷新、权限丢失和结果未知保留整个值，不合并分支。已有任务快照不变。
- 审批/办理支持有序规则和必选否则；CC、嵌套条件、发起自选、应用 provider 不支持。
- 标准来源只能在已有上限内编辑；复杂来源按精确发布/冻结引用选择。连续主管任何叶子都要求 sequence。
- 未完成新节点可存草稿，仅容许空的标准成员/角色输入；完整发布和办理覆盖仍严格校验。变量必须是节点所有路径可用事实，可选事实仅用于 exists。
- AI 提案也走相同 binding/canvas gate，不改变已发布 canonical binding 的所有权。

## 资源、失败和回滚

上下文按流程提供一次，避免每个节点复制定义。最多20规则，16KiB/AST预算不变。旧平台缺上下文/标志则关闭编辑，不尝试降级成平铺来源。回滚先关闭平台 capability/catalog，再回退 SDK；已保存条件不能静默丢失。

## 可证伪验收

新增审批/办理规则、排序、否则、标准/引用来源；无编辑打开不能产生脏状态；readonly/CC不写入；冲突刷新不拆分 assignment；未知结果重试同一操作；可选/非支配变量、非法来源、超限、错误 mode 被拒绝；草稿空成员可保存但不能发布。最终配合真实角色、正式 contracts 与平台组合验收，本 ADR 不代表验收已通过。
