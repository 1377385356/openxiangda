# 共用人员绑定的节点级主管校验隔离

## 问题与实证

合同风险处理的受理和复核节点共用office绑定。真实应用四流集成检查（SDK2.74.0/contracts2.95.0）给受理节点选择连续主管并同时改为sequence，却返回WORKFLOW_SUPERVISOR_CHAIN_SEQUENCE_REQUIRED:office_review。被编辑节点已满足规则，未编辑复核节点被错误纳入。不是组织数据缺失，也不以新增业务绑定或修改另一节点绕过。

## 所有者与不变量

共享contracts唯一拥有普通/条件来源的准入与事实校验，后端仍持有已发布目录和原子节点覆盖，应用不实现替代校验。节点覆盖投影已经使用平台保留的$administration节点绑定，编辑单节点不改变同名源码绑定的其他引用。全局源码绑定的主管规则仍对所有真实引用生效，不能因修复而放松。

## 修复与边界

叶来源验证时在独立浅拷贝中只为目标节点分配保留的临时绑定键，再复用现有主管校验器。保留完整原图和动作输出schema，节点事实的可用性/支配关系、模式、人数、部门上下文与发布目录限制不变；不修改输入对象、存储或运行时任务。source binding不允许$，临时键不与真实源码来源冲突。无新增HTTP、身份、SQL或持久状态；V1不受影响。

## 可证伪验证与交付

回归：两个节点共享office，单节点连续主管/sequence通过，另一节点保持single和原来源；普通和条件两入口一致。全局把共享绑定改为连续主管时，另一个single节点仍必须被拒绝。现有未来步骤事实、缺组织、越界与失权测试继续通过。四流真实声明再验，之后按官方affected与发行门禁、不可变制品、平台组合/TEST和真实角色分别取证。
