# 审计权限引用保留已有能力所有者

会议应用使用已声明的管理端 UI capability 作为 `audit.read` 时，2.8.0
的本地 context 命令报告四次 APP_CONFIG_CAPABILITY_OWNER_CONFLICT。
编译器把四个系统审计列的权限引用当作资源的新 catalog 定义；此前测试只覆盖
自动创建的未声明能力，未覆盖设计规定的已有能力引用。

能力 catalog 仍由平台保留能力、显式 authz 声明和既有业务资源定义拥有。
四个系统审计列只引用完整 catalog，不定义或改变能力的 kind、name、source。
引用可以来自另一个资源，且不能依赖资源排序。编译器完成所有定义后校验引用
闭包；缺失和跨应用引用在本地及平台共享编译器均失败。业务字段和 CRUD 能力
原有的定义冲突规则保持不变，不能通过此修复放宽其他 owner 冲突。

这是原审计合同的实现修正。公开 devkit 与共享 contracts 同步发补丁版本，
平台锁定同一共享包。无新权限、身份、存储、查询、后台任务或并发行为；工作量
有界于已有资源、审计字段和能力数组。V1 与省略审计策略的 V2 应用不受影响。
修复可与应用候选一起回退；已采用受限审计的应用仍需保留支持策略的后端。

验证显式 UI 能力复用、跨资源引用及资源排序、同一能力被多个模型复用，确认
生成 catalog 中原 owner 精确保留且只有一项。未知引用在本地和平台失败；真实
重复 owner 仍失败。最后用会议应用原配置和正式公开包重新执行 context/check。
