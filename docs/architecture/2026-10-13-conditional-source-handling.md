# 条件人员规则的 Source v2 隐私往返

状态：承接已确认条件人员与源码同步方案；实现和验证中，不开放平台能力。

## 问题与所有者

v1 handling 只能表达角色或指定人员数量，条件覆盖因此被明确拒绝导出。
不能把全部覆盖直接塞进 canonical binding：那会泄露环境指定人员，也会
混淆源码默认值与覆盖。contracts 拥有可验证 DTO、纯投影与还原；devkit
拥有显式源码导入；平台仍唯一拥有实际人员、环境、版本、配置和发布。

## 决策与不变量

- 添加显式 `openxiangda.workflow-source-bundle/v2`，保留 v1 原语义和拒绝
  条件声明的守卫。canonical definition/binding 不被覆盖改写，摘要保持原值。
- v2 条件 handling 保留有序条件、标签和必填 otherwise。每个叶子是完整
  非指定人员 binding，或只有数量的 `named_people`。禁止嵌套、未知字段、
  指定人员 ID/姓名/运行解析快照。canonical 代码声明中的固定人员仍是源码，
  与环境覆盖的隐私边界不同，不能任意脱敏改变源码摘要。
- 任一叶子包含 named_people（包括 count=0），整个 assignment 不导入。
  返回明确的节点级警告，不部分合并角色分支，不编造人员或替换默认。
- 不请求采用 handling 时只导入 canonical 文档。显式采用时，复制规则前
  用原本地源码的已发布来源/冻结默认及节点上限，复用共享 node patch
  校验器；模式、事实类型/支配关系、复杂来源和范围均不能由 DTO 授权。
  每个节点独立绑定，不污染共享默认或其他节点。
- 先验证输入所有摘要、目录、结构和完整规则，再做内存修改，最后复用
  原导入的配置 CAS/路径/符号链接守卫。源文件和版本注册只有原所有者写入。
- DTO 校验可读取 canonical 条件声明；新增画布条件绑定仍受原 authoring
  admission 拒绝。平台 planner/public capability 保持关闭，不能用 DTO
  的可读性或离线导入通过冒充旧平台的执行能力。

## 限制、失败及回退

沿用 bundle 3 MiB、200 节点、条件 20 条/16 KiB及共享 AST 限制。
缺少 otherwise、错误类型、危险属性、嵌套规则、泄露字段、未知来源、
连续主管模式冲突和 code-owned drift 均失败；失败无文件写入。
不改 v1 应用或数据库。本轮服务端必须等官方 npm 制品验证/发布后才能消费，
禁止源码软链和私封 contracts。回退导入用 Git；新 DTO 老消费者明确拒绝，
不静默转换。生产部署不在授权范围。

## 可证伪验证

v1 行为不变；v2 条件顺序/标签/事实/非指定来源无损往返；未命中及否则
指定人员只保留数量；混合规则整体不导入；篡改摘要、泄露 ID、范围/来源
伪造、错误条件事实和连续主管模式拒绝；共享绑定隔离；不采用时声明摘要
保持；采用后源码 ahead/sourceBase 正确；导入失败不改文件。分别记录 SDK
受影响验证、官方 tarball、平台 exporter 与实际 PC/业务验收，不互相替代。

## 接入回归补充：普通单角色 handling

服务端混合流程实测发现 v2 decoder 把 legacy `roles: [one]` 直接当作
`roleCodes` 并集，触发并集至少两个角色的校验。该 DTO 不是并集声明；
恢复时单角色归一化为 `roleCode`，两个及以上仍使用受限 `roleCodes`。
不放宽条件叶子、权限或并集上限；空/重复/非法角色仍拒绝。普通 CC
继续用原角色/人数表示，不强制进入条件节点语义。补充纯契约混合流程
回归和平台 exporter 回归，正式制品发布前平台不得绕过共享校验。
