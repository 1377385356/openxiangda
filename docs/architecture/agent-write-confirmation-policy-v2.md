# 业务 Agent 写能力确认策略

## 问题与证据

预发试验报修任务已经由用户明确要求“帮我提交”，地点辅助查询也返回唯一地点，但 Agent 仍回复“请确认提交”。该应用的 Catalog 将普通 `write` 固定编译为 `confirmation: required`；当前声明没有选择权。重复确认阻断了用户批准的自动办理路径。

## 所有权与不变量

应用拥有业务任务、必填信息、歧义规则和是否要求业务确认；平台拥有身份、角色并集、应用 Head、执行幂等、会话和审计。此次只允许应用显式为普通 `write` 选择 `confirmation: none`，缺省保持 `required`。`destructive`、`external` 仍必须确认；`read` 不确认。用户必须明确提出办理，缺项或歧义仍先询问。免确认不改变授权、输入 Schema、AppVersion/Catalog 摘要绑定、服务端业务校验或幂等。

## 契约、失败与边界

`backend.operations[].ai.confirmation` 可选 `none | required`；Catalog 保留确认值，普通写仍要求 `idempotency: required`。无效风险/确认组合在配置和 Catalog 校验时拒绝。平台 Agent 使用既有受管直接执行路径；传统 MCP 预览/确认客户端契约不在本轮改动范围内。旧应用省略字段时字节语义不变；回退新工具链与试验应用预发 Head 即可停止新免确认调用，已有试验单保留供核对。

## 可证伪验证

编译器测试验证显式普通写 `none` 和缺省 `required`；契约测试拒绝破坏性免确认，接受普通写免确认且幂等必填。试验应用在预发以明确办理语句生成单号，同请求键重放仅得原单，缺项/歧义不写入，无权身份不能发现或执行。
