# Simple Application Delivery V2

状态：已确认实施，2026-09-12

## 问题证据

应用发布曾把 Git 主线、AppSpec 关联、全量脚本、摘要缓存、镜像构建、制品密封和平台激活串成一条长事务。任何一个后置门禁失败都会要求重新提交、重新构建和重新发布，开发反馈不可接受。

## 决策

- `openxiangda deploy` 只负责读取当前工作区、编译配置、执行必要的本地脚本、构建制品并提交平台部署。
- 不要求当前分支名称与远端默认分支一致，不要求提交已进入远端主线，也不阻止脏工作区进行测试发布；源码状态仍按真实值写入包元数据。
- 删除 Devkit 自己维护的工作区全量摘要、验证凭据和不可变候选复用逻辑。pnpm、Docker 和平台可以继续使用自身缓存。
- 保留平台配置兼容性、运行配额、后端镜像格式和 DeploymentRun 的基本幂等/重试能力；这些是平台运行所需，不是应用开发流程门禁。

## 所有权与不变量

- 应用负责业务声明、代码和测试；Devkit 负责编译、构建和提交；平台负责环境、权限、运行状态和回滚。
- 发布失败不得伪造成功，但修复后可以直接再次发布；不要求先完成额外的 Git 或本地摘要迁移步骤。
- 平台仍以 DeploymentRun 作为状态来源；网络重试使用已有运行状态，不创建额外的本地状态源。

## 影响与回滚

本决策影响 Devkit 的源码检查、部署编排和相关测试，不改变 AppPackage 字段或平台授权语义。回滚方式是恢复本文件涉及的 Devkit 提交；已创建的 DeploymentRun 仍按平台现有 retry/rollback 处理。

## 验证

运行 `pnpm --filter openxiangda-devkit-core check` 和 `pnpm --filter openxiangda-devkit-core test`。重点验证任务分支、脏工作区和重复发布均可进入构建流程，同时配置不兼容、缺少 Docker 或平台配额不足仍能在写入前失败。
