# 可选真实预发身份验收 v2

## 问题证据

- 平台已有真实测试用户、应用角色分配、一次性 verification login ticket 和真实平台 Cookie 会话能力，但它们仍暴露在 1.x 风格接口中，AI 无法用一个 2.0 命令稳定准备角色矩阵。
- 模板浏览器测试可以覆盖交互，却不能证明预发的真实登录、角色并集、字段权限、RLS 和 App Gateway 链路。
- 把真实身份验收设为每次发布硬门禁会引入登录、浏览器和外部环境延迟，放大发布时长与偶发故障。

## 决策

### 能力所有者

- 平台用户、应用角色和登录会话仍由平台身份系统唯一管理。
- 平台提供仅限 `preproduction` 的 2.0 acceptance identity prepare API；CLI 提供 `openxiangda accept --plan <file>` 作为 AI 的手动入口。
- 验收计划只声明 actor key、显示名、角色代码、有效期和安全 redirect；平台解析真实角色 ID、创建或更新真实测试用户，并签发一次性短期登录链接。

### 稳定不变量与受影响合同

1. 该能力永远是显式手动测试，不被 `check`、`build`、`deploy`、`promote` 或 `verify:release` 自动调用。
2. 只允许预发环境；生产请求在客户端和服务端双重拒绝。
3. 调用者必须是已登录的平台管理员，测试用户只能获得当前租户、当前应用中计划声明的角色。
4. AI 输出是机器可读结果：每个 actor 返回真实 userId、解析后的 roleCodes、账号过期时间、一次性 loginUrl 和链接过期时间，不输出 Cookie、access token 或 refresh token。
5. 重复使用相同 actor key 是幂等更新，不创建无限账号；单次计划 actor 数量和有效期有硬上限。

### 失败、并发、安全与资源边界

- actor key、角色代码、redirect、环境或有效期不合法时整次请求在写入前失败。
- 单次最多 12 个 actor；默认有效期 4 小时，最长 24 小时；登录票据保持短期且只能消费一次。
- redirect 继续复用平台同租户域名和显式允许的本地开发 origin 校验。
- 平台对准备与票据消费写审计；CLI 不持久化登录链接到工作区。

### 回滚边界

- 删除 2.0 API/CLI 不影响平台正常登录和发布链路；已有测试用户按其有效期自然失效。
- 不修改 1.0 应用或 1.0 发布协议。

## 可证伪验收

1. `openxiangda accept --plan ... --json` 为两个不同角色生成真实、不同 userId 的一次性预发登录链接。
2. 两个链接分别进入真实预发应用，权限矩阵、字段可见性、RLS 和 App API 动作结果符合声明。
3. 重放已消费链接失败；超过有效期的账号不能登录；生产环境计划在任何写入前失败。
4. `openxiangda check`、`deploy` 和发布验证的调用图中不存在 acceptance API，平台 acceptance 服务不可用时发布仍可完成。
