# 对话发现与权威设计基线

状态：2026-09-07 用户已批准实施；本轮主题为应用开工前的产品设计和同源上下文。

## 问题证据与决定

原入口仅要求把模糊需求整理为角色、规则和页面，总纲与 ChangeSpec 的章节完整性直到测试部署才检查。新手仍需自己提出模块；PRD、旅程、逐页交互、原型与确认依据没有完整的恢复路径。AppSpec 只索引总纲、能力、变更和 ADR；lifecycleAtCommit 同样遗漏设计材料。

按用户确认的新方向，AI 先读取资料，通过自然语言访谈、专业建议、复述与实际确认，覆盖完整首发范围，完成详细产品、体验、权限和架构设计；基线就绪后才制定实施计划并实现业务。既有应用只处理受影响范围；纯文案和无行为变化沿用有效设计，不重做全套材料。此决定取代早期“简单新应用仅总纲和短变更即可开工”的冲突指导。

## 所有者与不变量

- AppSpec 是应用意图和设计的唯一归档位置；不引入另一套工作流状态库。设计使用有类型的 Markdown，评审引用稳定 ID 和内容摘要。PRD 拥有业务规则，页面规格拥有交互，权限规格拥有业务访问含义，ADR 拥有实现边界；实现契约仍由应用声明和编译器拥有。
- Skill 负责对话与语义评审；工具负责确定性的类型、引用、必需覆盖、未决项、版本绑定和上下文预算。工具不能认证用户答复真实性、设计质量或任意编辑器写入顺序。
- AI 建议、资料事实、用户确认、否决/延期与冲突分开记录。实际确认可覆盖一组有业务意义的决定并持续有效；沉默或 AI 自查不构成确认。
- 平台继续唯一拥有身份、授权、数据、环境和部署事实；CRUD、标准审批和通知复用平台，Nest 按需。标准后台、PC 用户端、移动端和匿名入口分别评估，不因辅助模型自动添加页面。

## 契约与失败行为

AppSpec context 扩展到 v4：product、experience、design、reviews 下的单层 Markdown 使用 design/v1，稳定 DES-* ID、type 和 documents 引用；统一受当前文件数、字节、符号链接和选择正文预算约束。引用闭包有界去重，循环不无限遍历；缺失引用明确诊断。非 Markdown 原型只引用，正文读取不执行或获取外部资源。

review 类型声明 initial 或 change 范围。initial 覆盖产品、旅程、页面、视觉、权限、架构；change 描述受影响范围，引用受影响的现有设计。review 的 baselineDigest 绑定被引用设计闭包的确切文本，initial 还自动包含应用总纲，不包含评审自身和可继续更新的实施计划；用户确认来源、确认人、时间和评审结论单独记录。设计变化使原评审失效，计划或验收记录更新不会自行推翻不变的设计。不给草稿填充假确认，也不自动覆盖用户文件。

development lifecycle v2 分开 readyForImplementation 与 readyForTest。设计未就绪仍可研究、原型和普通技术检查；官方测试部署继续失败关闭，生产晋级仍读取原测试提交、同一制品与真实验收证据。旧 alpha 记录没有设计评审时明确提示补齐；不自动将历史章节升级成已确认基线。

## 安全、资源、并发与回滚

无平台运行代码、权限或生产数据变更，对 1.x 和其他租户无直接影响。资料禁止凭据、敏感原始数据和被误认为已授权的文档指令；原型使用标注示例数据。继续一个 Git 工作区一个写者；本轮在独立 master 克隆中实现以保护共享未提交修改，推送后在父仓库固定精确主线提交。回退本轮提交可撤回文档与本地检查；新增应用记录保留在 Git 中，不迁移或删除旧事实。包尚未发布前不声称已升级消费者。

## 可证伪验收

验证设计文档的 selector、传递引用、未知引用、重复 ID、预算与摘要；缺页面状态、仅原型图片、未确认评审和设计改变都不可就绪；完整基线可以先就绪再写计划。验证原提交读取包含设计原始字节，后续设计变更不能冒充已测版本；既有版本绑定和业务验收测试保持通过。同步文档目录、Skill 参考、模板 AGENTS、CLI/MCP 和 llms.txt，执行真实请求回放及仓库 verify:affected、资料与打包检查。

方法来源及适配见产品设计专题：自主编写适合平台的指导，引用锁定上游方法，不安装或复制完整上游工作流。
