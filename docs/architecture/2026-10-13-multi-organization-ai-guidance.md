# 多组织平台能力的 AI 发现与使用指引

状态：2026-10-13。维护者资料接入决定；组织接口使用配套修正的 V2 命名空间，不新增运行时权限能力，不代表 npm 发布或站点部署。

## 问题证据与能力所有者

平台服务器已具备真实钉钉组织注册、安装 reconciliation、成员投影、家校目录角色事实、平台会话组织切换及当前用户授权响应中的组织上下文。但 V2 中文专题目录和入口 Skill 没有相应场景路由。AI 遇到教育局与独立学校组织、多校家长、多组织教师时，可能重复建设组织与身份体系，或误以为组织树已自动进入 Data API 权限。

源码核对发现：浏览器 `validateRuntimeAuthorization` 尚未投影 `activeOrganizationId`，Nest `OpenXiangdaCurrentUser`/`currentUserFromPrincipal` 尚未提供该字段；目录角色事实尚无完整应用读取和映射入口；V2 角色声明和 Native Data API 尚未执行组织 reach。文档必须同时揭示可调用的 HTTP 契约与这些边界。

平台继续唯一拥有组织、安装、身份、成员、目录事实和授权。应用拥有业务模型、能力含义和使用目录角色的意图。V2 `DOCUMENTATION_TOPICS` 唯一拥有中文使用专题目录；Skill references、CLI/MCP 文档和根包资料继续由既有生成/分发机制提供。

## 不变量与受影响契约

- 场景导航引向 `multi-organization` 同一正文，不建立另一份领域能力 catalog。
- 已实现源码、应用可调用入口、SDK 封装、待接通权限和目标站点部署状态分别描述。
- `corpId` 仅作为入口线索；应用不伪造用户、unionId、成员关系、授权上下文或第二份组织树。
- 组织切换保持当前人的身份，区别于角色选择和只读 Perspective。
- `organizationReach=self|subtree` 是组织覆盖意图；当前不是可使用的 V2 config 字段或自动行隔离。
- 不把平台管理/upsert API 当普通应用的读取接口，不给应用新增平台管理员授权。

受影响契约仅为资料主题目录、同源 Skill 路由、工作区 AGENTS 模板和文档站导航。稳定 1.x 运行时、其他租户数据和现有应用声明不变。公开包资料变更通过 Changeset 进入后续发行；本轮不发包。

## 失败、并发、资源与安全边界

文档主题沿用固定白名单、128 KiB 上限、版本/摘要校验和章节读取；不存在新的网络代理或凭据存储。HTTP 示例仅查询当前会话自己的组织成员，检查 HTTP 状态和响应 `code`，不记录 profile 或 token。组织切换说明要求服务端验证成员，成功后废弃旧组织界面/请求结果并重读，失败不能在浏览器先切换身份。

Mac 为唯一源码写入位置。重型验证可从已提交推送的 Git 主线组合同步到干净 WSL checkout 执行；不复制未提交平台源码，不停止无关服务。

## 回滚边界与可证伪验证

可独立撤回专题注册、指引和导航，不回退数据库或修改任何授权事实。下列任一失败都否定本轮资料接入完成：

1. CLI 文档目录不包含 `multi-organization`，或无法读取其全文/指定章节。
2. MCP `docs_read`、资料目录或 `openxiangda://docs/multi-organization` 返回不同来源的正文。
3. 生成的 Skill reference、llms 索引或发行资料摘要与官方正文不一致。
4. Skill 无法按教育局/学校、多校家长、多组织教师等任务找到该专题。
5. 文档将未导出的 SDK 字段、目录读取接口或组织 RLS 写成现有可用能力。

使用既有同源资料检查、Skill 校验、文档分发测试及真实 CLI/MCP 只读入口验证；文档站检查链接与构建。源码检查、资料分发与真实组织业务验收分别报告。
