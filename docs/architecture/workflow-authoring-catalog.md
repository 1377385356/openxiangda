# Workflow canvas capability authoring

Problem: human insertion cloned existing nodes, missing independent blank-node configuration; action inputs were fixed to a previous node, while the inspector hid available controls. Task reminders also lacked the designed unit/confirm interaction.

Owners: the active application workflow projection owns released pages, assignment source implementations and business handlers. The platform owns standard human-node operation/mode rules, directory identity, authorization and publication. The SDK edits canonical definition + binding together; diagram coordinates are a projection only. A derived, version-labelled catalogue is a read, never a new state store or a trusted client input.

Fresh nodes use `canvas_<nodeId>` binding keys. Their people defaults and operation policy are versioned on first publication. After that, entered-task snapshots remain immutable, and node handling edits use the environment configuration owner, not a second draft binding write. Page field ceilings are declared independently of existing nodes. No task page means standard read-only detail, with no save-form action. Existing source-owned node minima and limits remain enforced.

`authoring.businessSteps` declares unused capabilities with fixed handler/version/mode/input/output schema; it is code-owned. It participates in handler manifest/subscription validation even before a graph uses it. Canvas input mappings may change, handler contracts may not. Source bundles retain canvas-created binding entries; provider/page/handler implementations remain code-owned.

Save validates strict document shape and capability authority, retaining explicitly incomplete member selections or mandatory step mappings with diagnostics. Publish remains strict, re-reads the active catalogue under the existing management scope/lock/CAS, validates directory identities and application roles, and then uses the version registry/activation owner. Unknown mutation results retain the original operation id. Default publication is running-and-new; task-entry E remains frozen while routing R changes. No manual approval gate or runtime JavaScript editor is added.

Bounds: 200 nodes/bindings, 3MiB documents, 100 released steps, 200 users per binding, 8 roles per union, 32 expression levels/1024 evaluation operations, 20 hypothetical examples. Existing step mapping, type and every-path output checks remain authoritative. Example state is local and never enters a version. Return eligibility is advisory in the UI and must still pass executable validation.

Reversible boundary: UI and authoring contracts are additive; no schema migration, production activation or npm publication is part of development. Old explicit node limits are not silently expanded. Conditional people composition is a separate executable-provider item, not satisfied by static inspector controls or example evaluation.

Verification must falsify template dependence, schema/field/operation escalation, unreleased handlers, bad principals, save/publish incompleteness, binding-only undo and source import/export drift. Browser synthetic previews, service tests, deployment and real business-role acceptance are separate evidence classes.

Buffered inspector edits: reminder confirmation and invalid JSON literals are local input, not canonical persisted data. They participate in dirty/navigation guards, block publication and draft replacement, and never autosave an older value while presenting it as the new input. A node/version/assistant transition is refused with a corrective message until reminder confirm/cancel or JSON correction. Undo/redo and insertion cannot silently discard these buffers. Canonical changes continue to use the existing draft CAS and mutation ledger. Invalid literals remain bounded to 16 KiB and are never sent to the runtime. Test navigation refusal, explicit cancellation, confirmed reminder readback, and external undo restoring JSON text. This is additive SDK behavior, with no runtime/data migration or production effect until a deliberate publication.
